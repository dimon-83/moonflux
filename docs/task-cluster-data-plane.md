# 任务跑在集群数据面（P1-2 设计稿）

> 状态：**P1-2a 已交付**（决策 118 ✓）——运行日志进集群、`task logs --remote` 成立；**P1-2b 待实现**。
> 计划与优先级见 [dev-plan.md](dev-plan.md)；相关决策见 README 决策 104 / 116 / 117 / 118。

**P1-2a 落地情况（决策 118）**：`pipeline run` 的集群追加路径**早已存在**（`RunLog.append` + `append_to_cluster`），但挂在 `--state-remote` 上、runner 从不传它 ⇒ 日志一直留在工作节点。现在 runner 会把控制面同时作为 `--state-remote` 传给孩子；`task logs --remote <sc>` **先解析 leader 再去数据节点读**（控制面不提供数据读，实测 `unknown command 21`）；没有宿主时它**明说** `has no host yet`。
**仍然待办**：① **runner 自动声明**任务的运行日志主题（现在要操作员 `topic create` 一次）；② 数据路径（源/汇）进集群 = P1-2b。

## 1. 问题（当前的诚实边界）

一个被 runner 托管的任务，是 `pipeline run --name T --data-dir D` ——它读写的是**自己数据目录里的主题**：

- 判据与证据：决策 104 的边界段；门禁 `e2e-p49-docker-cluster.sh` 的动态腿里，任务的**输入/输出主题都在 runner 容器的数据目录里**；
- `task logs`（决策 106）读的是**那个数据目录**下的 `<task>.run-log`：它能把日志给出去，但前提是**你就在那台机器上**（或能挂到那个目录）。`--remote` 交给控制面的，只有运行**状态**（`RunRecord`），不是日志内容。

由此三件本该成立的事**不成立**：

| 期望 | 现状 |
| :--- | :--- |
| 从任何地方读任务日志（`task logs --remote`） | ✗ 日志在工作节点磁盘上 |
| 任务与数据同处一地（算力跟着数据放） | ✗ 任务只碰自己的本地主题，集群的数据面（spu）与它无关 |
| 多节点放置的**意义** | ✗ 目前只是"把计算放到某台机器"，与数据位置无关 |

## 2. 设计

**一句话**：给 `pipeline run` 一条**集群客户端**运行模式——任务的源、汇、运行日志、状态主题都走**既有的集群客户端**（`core/client` 的会话），**不新增协议、不新增端口**。

### 2.1 形态

```
moonflux pipeline run --name T --control 127.0.0.1:19900 [--token …]
```

- 与 `--data-dir` **互斥**（两种口径，各自完整）——沿用决策 34 的"两种口径不一样的话，不混着说"；
- 子进程由 runner 拉起（决策 95 不变），runner 把自己拿到的控制面地址与凭据**传下去**；
- 任务**不再持有数据目录**：它是一台**数据面客户端**。

### 2.2 四个数据路径

| 路径 | 现状 | P1-2 之后 |
| :--- | :--- | :--- |
| 源（`{"type":"topic"}`） | 本地主题 | 集群主题（**声明在集群**，spu 宿主） |
| 汇（`{"type":"topic"}`） | 本地主题 | 集群主题 |
| **运行日志** `<task>.run-log` | 本地主题 | **集群主题**（`task logs --remote` 于是成立） |
| 状态主题（`spec.state.topic`，P30） | 本地主题 | 集群主题 |

**主题声明**走既有路径：`topic create`（声明）+ 控制面调和出放置（决策 17–21）✓——**不发明第二套放置**。门禁 `e2e-p40-panels.sh` 里已经有"给集群声明运行日志"的先例。

### 2.3 进度与语义（最容易含糊的地方）

**主题源不提交进度**（决策 72 的边界）：`from: beginning|end|offset:<n>` 是"每次都从 spec 说的地方开始"。

- **P1-2a 不改这一点**：日志与状态都是**追加写**，起点语义无所谓；
- **P1-2b 必须面对它**：任务源若是集群主题、并且**停机期间的数据不能丢**，需要**持久进度** ⇒ 唯一有的答案是**消费组**（P9 已有：协调者、世代围栏、偏移持久化、心跳下发份额）。
  - 因此 P1-2b 引入**新的源类型** `{"type":"group","group":"g","topic":"t"}`：成员身份、提交、再平衡全走既有 `GroupRegistry`，**不新建第二套进度存储**；
  - 语义仍是**至少一次**（提交在处理之后；再平衡窗口内允许重复）——**不得声称恰好一次**；
  - 从 `end` 起的旧口径**保留**（有意重放/一次性任务用它），并由内核 `replay_warnings`（决策 112）继续对"重放 + 外部副作用"发警告。

### 2.4 鉴权

- 子进程用**客户端身份**连数据面（不是节点身份）——`Node` 身份只留给 REGISTER/HEARTBEAT/SYNC_*（决策 35）；
- 凭据由 runner 传给子进程（`--token` 或环境，走 `client_token` 口径，决策 46）；**凭据不进日志**（P12 纪律）；
- 需要细粒度时用**按主题 grants**（P21）：一个任务对自己的输入/输出主题有读写，别的一律拒绝。

### 2.5 失败语义（如实写下）

- 集群不可达 ⇒ 批次失败，**不落半个批**（fail-closed，P2 纪律），run-log 记 `failed`，任务按 `restart` 策略重启；
- 汇写成功但确认丢失 ⇒ **可能重复投递**（至少一次的推论）；
- **不做**：恰好一次、事务性多主题写、跨节点状态迁移。

### 2.6 明确不做（首期）

- 任务副本 / 自动扩缩容 / 滚动升级 / 亲和（P3，决策 100）；
- **不把节点变成任务宿主**：任务始终是**数据面的客户端**，不是数据面的一部分——把 runner 塞进节点循环会破坏 P13 的"一圈有多长"（决策 36）。

## 3. 第一片（P1-2a）：运行日志进集群

**为什么先做它**：它单独就能交付一个操作员看得见的收益（**`task logs --remote`**），而且改动面最小——只动**运行日志**这一条路径。

**要做的事**：

1. `pipeline run --control SC`：会话走 `core/client`，run-log 主题建在集群（声明 + 调和）；
2. `task logs --remote SC --name T`：读集群上的 `<task>.run-log`（**不再需要 `--data-dir`**）；
3. `task status --remote` 不变（它已经是运行表的投影）。

**判据（可证伪）**：

- 门禁：起 sc + 一个 runner，**在另一台"没有该任务数据目录"的进程里**（门禁本身就是）用 `task logs --remote` 读到该任务的运行日志**内容**（含 `run-start` 与至少一批 `batch`）；
- 反例腿：`--data-dir` 口径**行为不变**（本地任务的日志仍在本地，且 `task logs --data-dir` 照旧可读）；
- 边界腿：任务所在节点**不可达**（杀掉 runner 容器/进程）时，`task logs --remote` 仍能读到**已写入**的部分（因为真相在集群，不在那台机器上）——这正是本片要买的东西。

## 4. 第二片（P1-2b）：源与汇进集群

**判据（可证伪）**：

- 三个节点（sc + 2 spu）上起一个任务，任务的输入主题由 **spu 宿主**（不是任务本地）：`produce --remote` 写进去的数据，任务读得到；
- 任务输出落在集群主题，`consume --remote` 读得到，**逐字节一致**；
- 用 `{"type":"group"}` 源：**杀掉任务再起**，从**已提交偏移**续读（缺口 = 0，重复允许），与 P9 的组门禁同源；
- 反例腿：`--data-dir` 单进程口径**逐字节不变**（p0/p1 的现有门禁全绿即证）。

## 5. 风险与开放问题

1. **任务进程的形状**：现在 `pipeline run` 是"单进程跑一条管道"；接集群后它需要 **poll/泵** 才能不阻塞（P13 的教训：等对端时要继续服务自己的连接）。这是一次真正的结构改动，**不是加个参数**。
2. **同机多任务的连接数**：每个任务一条（或数条）到 spu 的连接；`MOONFLUX_LOG_CACHE` 那类**有界**纪律要同样适用（铁律 1）。
3. **运行日志的写入者唯一性**：日志由**子进程**写（一个任务一个写入者，P36），runner 只透传——不得出现第二个写入者。
4. **控制面不可达时**：任务应当**继续跑**（像 P11 的"控制面消失仍服务"）还是停？倾向**继续跑**，run-log 写不进去时按结构化错误记一次（每个原因一次，不刷屏）。
