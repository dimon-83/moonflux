# SDF 缺口追平方案（逐条：追平 / 变通 / 不做）

> **定位**：对 [`sdf-examples-port.md`](sdf-examples-port.md) §4 的**九条缺口**逐条给出结论与方案——哪些可以补齐 moonflux 的能力追平、哪些能用既有机制变通、哪些应当显式不做，以及每条的**设计要点、门禁形态、代价与风险**。**规约依据**：AGENTS.md §5（内核红线：确定性、零 IO、零第三方依赖）、§7（对标规则：不把参考系统的默认假设当规范）、§8.1–8.2（算子与函数集纪律）、§9（不做清单）。**边界声明**：本文是**方案与判定**，不是承诺——除已标注"已具备/已实测"者外，其余均**未实现、未立项**；每条都标了建议的规模（小/中/大）与依赖顺序。
>
> **日期**：2026-10-10

| :--- | :--- | :--- | :--- | :--- |

## 2. 逐条方案

### 缺口 1 · 服务内持久键控状态 —— 可追平，且不必新造存储

**现状（事实）**：算子是无状态纯函数（guest 无导入、无时钟、无随机源），宿主不持有 per-key 状态；平台上唯一的持久真相是分区日志。

**设计（事件溯源式状态，复用既有四件套）**：

1. **状态就是一条压实后的键控主题**。所有状态变更都是记录：`(key, 新值)` 追加到 `topics/<state-topic>`；压实（P14）天然给出"每键最新"；复制（P3/P7）天然复制状态；恢复 = 重放该主题（上界 = 键数，不是记录数）。**不需要新的存储引擎、不需要新的复制面**。
2. **ABI v3 加法（成对导出，沿用 v1/v2 纪律）**：`mf_op_state_abi_version` + `mf_op_state_apply`。宿主负责：按 spec 的 `key` 取键 → 从**本地状态视图**取该键的当前值 → 把 `(records, 键, 旧值)` 交给 guest → 收 `(records_out, 新值)` → 追加到状态主题并更新视图。**guest 仍然没有导入**：状态是**数据进、数据出**，沙箱的纯函数结构性事实不被破坏（这是本设计相对"给 guest 一个 KV API"的关键优势——后者要给 guest 加导入，等于改写决策 16）。
3. **确定性**：状态转移只依赖输入记录与旧值，二者都是确定的；旧值由"同一主题的重放"决定 ⇒ 同一输入重放出同一状态。这是能够设门禁的前提。
4. **地板与保留**：状态主题的 retention 由应用给定（与 P8/P28 同源）；压实只删被取代的记录，**绝不删每键最新**，因此状态主题的 floor 语义是"最后一版"。
5. **跨服务状态读**：今天的诚实变通是"另起一个消费者读那条状态主题"；追平可加**宿主侧 `lookup` 变换**（键来自记录 → 读状态视图 → 合并/替换），它属于 adapters，不进沙箱。

**门禁形态**（结构事实，可证伪）：状态跨进程重启存活（重放状态主题后同结果）；状态主题被压实后最新值不变；两副本各自重放得到逐字节一致的视图；同输入重放两次结果逐字节一致；未注册状态主题/缺键/坏 ABI 版本都 fail-closed；状态主题的 retention 不影响最新值。

**代价与风险**：状态主题的键空间无界 ⇒ 需要视图上界（LRU + 重建），要写清"视图是缓存、主题是真相"；写放大（每变更一条记录）；`key` 的提取规则必须显式（不能靠签名嗅探——SDF 的 KVIO 靠签名推断是我们要避免的那类隐式约定）。

**推荐**：**追平**，作为独立里程碑（含 ABI v3 设计稿先写后做，照 P26 的"先改稿再改码"）。

**设计稿已出（2026-10-10，T113）**：[`operator-abi-v3-state.md`](operator-abi-v3-state.md)——状态 = **压实过的键控主题 + 宿主视图**（复用日志/复制/压实/floor，**不引入第二份持久真相**）；ABI v3 = **加法段**（输入/输出信封各多一个状态段，成对导出，v1/v2 不受影响）；窗口无需宿主特性（键 = `key@窗口起点`，水位 = 已见最大事件时间，无 idle 触发器——与参考系统自己的文档边界一致）。§6 给出 11 条可证伪门禁形态，实现阶段（T114）逐条落地。

### 缺口 2 · 窗口与水位 —— 可追平，但照抄参考系统的边界（含它自己的缺口）

**现状**：没有窗口、没有水位；记录带 `timestamp`（宿主在入口注入），因此**事件时间是可确定计算的**。

**设计（建在缺口 1 之上）**：

- **窗口 = 键空间的一部分**：状态键取 `(key, window_start)`；窗口终态由"已见最大事件时间"（水位）推进触发写盘（水位是输入的函数 ⇒ 确定）。
- **水位 = 单调推进的已见最大事件时间**，与 SDF 相同：**没有 idle 触发器**（SDF 自己的 `word-counter` README 就把这写成已知缺口）。这不是我们抄来的缺陷，而是"确定性 + 无宿主时钟"下的自然选择；页面上要写清"窗口只在有更晚事件时闭合"。
- **输出时机**：由"新记录到达且水位跨过窗口末端"触发（不是定时器）。宿主 tick 只做清理，不做发射——避免把墙钟接进语义（决策 33）。

**门禁形态**：同一输入两次运行输出逐字节一致；乱序记录不改变闭合结果（水位单调，迟到记录按既定策略计入或丢弃并**报告**）；跨窗口边界的记录不重复计入；`MOONFLUX_*` 关闭时无窗口行为。

**代价与风险**：迟到记录策略必须显式（丢弃并报告 / 计入并重发——SDF 未定义，我们要定义并留痕）；水位状态本身也是状态（要么内存可重建，要么进状态主题）。

**推荐**：**追平**，紧随缺口 1；**不引入定时器语义**。

### 缺口 3 · SQL 引擎 —— 不做引擎；给三条变通路径

**现状（事实）**：mbel 有 `fromJSON/toJSON/get/keys/values/fromPairs/toPairs/type` 与 `mean/median/max/min/len/flatten/map/take/uniq/sort/join/split/replace/indexOf/...`；批算子可做**批内聚合**（N 条进、1 条出）。

**判定**：**不引入 SQL 解析器与查询引擎**（保留意见见 `sdf-examples-port.md` §5：查询是消费方的事，把 SQL 放进平台要重定义"谁拥有状态"）。变通三条：

1. **规则内聚合/投影**：`fromJSON(value)` 取字段、数组内建聚合、`toJSON(...)` 拼回——覆盖 SDF 示例里绝大多数"查询"用途（字段投影、过滤、去重、排序）。
2. **批内聚合算子**：真正需要 `GROUP BY` 形态的，写成 wasm 算子（批进批出、N→1），语义与门禁都在算子那一层（`crosscheck-operators.sh` 已有对拍骨架）。
3. **状态主题查表**（配合缺口 1）：`lookup` 变换做点查；跨主题 JOIN 仍是消费方职责。

**门禁形态**：变通 1/2 由既有 `e2e-p29-examples.sh` + `crosscheck-operators.sh` 覆盖；不新增 SQL 门禁（没有 SQL）。

**推荐**：**不做**；在文档里把"为什么不做"写死（避免下一轮有人"顺手加一个 SQL"）。

### 缺口 4 · schema 类型语言 / codegen —— 原语已具备，只差一处修复

**现状（实测，这是本轮最值钱的一条）**：
- `fromJSON` / `toJSON` / `get` / `fromPairs` **都在**，且字面量可用：`toJSON(fromJSON("{\"a\":1}"))` → `{"a":1}`；
- **唯一拦路石**：发布期静态检查用 `value = "a"` 作为探针（`apps/transform/transform.mbt` 的 `compile_with`），于是 `fromJSON(value)` 在 `apply` 期就被判 `static check: fromJSON: invalid JSON`——**把"运行期才知道的值"当成了"编译期已证伪的常量"**。

**设计（小票）**：静态检查的探针改为**合法 JSON 形态**（如 `{}` 或一小组 `{}` / `[]` / `"s"` / `1`），并且：

- **保留 fail-closed**：**字面量**坏 JSON（`fromJSON("a")`）仍在发布期报错；
- 运行期仍按原语义失败并 fail-closed（`apply_chain` 已如此）。

**门禁形态**：wbtest + 门禁腿：`{"expr":"toJSON(fromJSON(value))"}` 能 apply 且运行正确；`toJSON(fromJSON("a"))` 仍在 apply 期被拒；`get(fromJSON(value), "ssn")` 能取字段（用例即案例 01 的字段级版本）。

**副作用（正向）**：案例 01 可以从"十个嵌套 replace"升级为**真字段级掩码**（`toJSON(fromPairs([...]))`），与 SDF 的 `u.ssn` 语义对齐；`json` 一族的 SDF 示例（字段改名、投影）从"不可移植"变成"可移植"。

**风险**：任何"用探针求值做静态检查"的方案都带一个关于输入的谎言；干净的长远形态是 mbel 提供**只检查不求值**的入口（上游候选，本仓库不复制其源码）。当前改动把谎言从"不是 JSON"缩小到"是合法 JSON 但内容未知"，并把**类型/名字检查**的职责保持完整。

**推荐**：**立即做**（九条里性价比最高的一条）。

**落地（2026-10-10，T108）**：探针不再是一个字面量，而是**两个由表达式自己命名的形状**——`{"k":"k"}`（字符串）与 `{"k":1}`（数值），任一成立即允许发布。理由：探针是对输入的一个断言，而**没有任何单一断言能同时服务** `replace(get(...), "-", "*")` 与 `get(...) > 60`；表达式自己声明了它要哪种。字面量坏 JSON、类型冲突与未知名在**两个形状上都不成立**，因此仍然被拒（`scripts/e2e-p1-rules.sh` 两条腿钉住双方）。案例 12（`custom-serialization`）三腿是它的端到端证据，含 **恒等往返**（`toJSON(fromPairs(toPairs(fromJSON(value))))` 逐字节等于输入）。实测：`get(fromJSON(value),"mph") > 60` 在数值形状下通过并在真实记录上给出 `true/false`；`value + 1` 仍在 apply 期被拒。

### 缺口 5 · Rust/SmartModule 工具链 —— MoonBit 层已有等价物；补齐的是"作者面"

**现状（事实）**：moonflux 的 guest 用 MoonBit 写（`apps/operator-sdk` + `apps/operator-*`），编译到 classic `wasm`，**必须无导入段**（探针以 WAT 为真相源），ABI v1（批）+ v2（标量）成对导出，fuel 预算、fail-closed、双后端对拍全部就位。也就是说：**"可编程扩展"的能力早已存在，缺的是"给外部作者的入口"**。

**判定与方案**：

1. **写一份"如何写一个算子"的指南**（对标 SDF 的 `packages/_hello-world_`）：从 SDK 起步 → `moon build --target wasm` → 探针自检 → 挂进 spec → 跑门禁。这是**小票**，且直接回答"工具链是否可替代"。
2. **发布稳定的 C ABI 头**（把 `core/operator` 里的 `mf_op_*` 常量与信封格式固化成 `.h` + 一页说明）：任何能产出**无导入 wasm** 的语言（Rust/C/AssemblyScript）都能写 guest。**这不需要把 Rust 纳入本仓库依赖**——guest 是用户代码，沙箱约束的是"无导入"，不是"必须 MoonBit"（AGENTS §1.1 的依赖合规约束的是**本仓库的产物**，不是外部作者的选择）。
3. **不做** `wasm32-wasip2` / 组件模型 / WIT：AGENTS §9 明确列为不该首期引入的方向；且 WASI 会带来导入段与 IO 能力，直接摧毁"纯函数"的结构性事实。
4. **不做**在仓库内提供 Rust 构建链（crates.io 解析、`sdfg` 式 proc-macro）：那是把参考系统的工具链假设搬进来。

**风险**：C 头一旦发布就是契约（照 AGENTS §8.1："要改 ABI 就升版本号"）；无导入约束会让 Rust 作者需要 vendored 依赖（用户侧决定，文档里写清）。

**推荐**：**指南 + C 头**（小–中）；**不做** wasip2/组件模型。

### 缺口 6 · split 拓扑（一源多汇）—— 建议追平，规模中等

**现状（事实）**：spec 只有一个 `sink`（解析层显式校验 `["source","transforms","topic","sink"]`）；SDF 的 split 是"一服务多汇 + 每汇自己的 transforms"。

**设计**：把 `sink` 从单值扩为**数组**（加法：`sinks: [...]`，旧文档的 `sink` 继续有效），每个汇可带自己的 `transforms` 链；执行面在 `pipeline run` 的 sink 阶段按汇分派（同一批记录分别过各自的链）。语义要点：

- **不是新算子**：它是拓扑（记录分发到多条链），因此不碰沙箱；
- 与"一节点一份已应用拓扑"不冲突（还是一个 spec、一份拓扑）；
- 偏移语义不变（写入主题的记录是原始批；各汇的变换在**输出侧**，不改变日志）。

**门禁形态**：两汇各自字节正确；一汇变换失败时**该汇 fail-closed 且不影响另一汇**；只有 `sink`（旧字段）的文档行为逐字节不变（回归腿）；`sinks` 与 `sink` 同时出现按名字拒绝。

**推荐**：**追平**（中票）。它把 SDF 的 `split/filter`、`split/filter-map`、`split-sentence`（双汇）三类示例真正对上。

### 缺口 7 · pipeline 以主题为源 —— 架构级，建议先不追平

**现状（事实）**：spec 的源只有 file/http/stdin/mqtt/kafka；没有 `{"type":"topic"}`。因此"主题→主题"的服务形态目前靠**服务端取数路径上的已应用拓扑**（决策 10）表达。

**为什么它是架构级**：给 pipeline 加主题源，等于让**节点变成它自己日志的消费者**——立刻需要：消费进度（谁记住读到哪了：要么进消费组，要么每条 pipeline 一个偏移文件）、与"一节点一份已应用拓扑"的关系（拓扑是节点级，而主题源是逐 pipeline 的）、写入自己主题的环状风险（源与汇同名）、以及与已应用拓扑的变换叠加次序（消费侧变换 + pipeline 变换叠加是否幂等）。这些问题都有答案，但每一个都要显式定义与留痕。

**替代路径（推荐先做的）**：

1. 用缺口 6 的**多汇**覆盖 split；
2. 用**状态主题 + 消费者**覆盖"主题→主题"的绝大多数用途（状态物化、跨服务读、JOIN 的输入侧）；
3. 需要真正流处理程序时，用 **CLI 消费循环**（`consume --follow` + 变换）表达，并把它作为**文档化模式**而不是新语义。

**判定**：**不追平（暂）**；若将来要做，按里程碑立项，先写设计稿回答上面四个问题。

### 缺口 8 · 函数集没有本地创建路径 —— 纯产品缺口，直接补

**现状（实测）**：`function-set create/get/list/delete` 只接受 `--remote`（缺了就报 `missing required flag --remote`）；单机用户必须先起一个 `serve`（哪怕只为把资产写进自己的 data dir）。案例 1 的步骤里保留并注明了这个绕法。

**设计（小票）**：给这四条命令加 `--data-dir` 口径（与 `pipeline apply --data-dir`、`topic ... --data-dir` 同形），复用本地元数据存储；`--remote` 与 `--data-dir` 互斥（同时给按名拒绝）；审计/权限路径不变（本地路径本就不经认证）。

**门禁形态**：无 serve 也能 `create` → `list`/`get` 可见 → `pipeline apply` 解析成功 → `pipeline run` 变换生效；`--remote` 与 `--data-dir` 同时给被拒；本地与远端同名资产的 revision 语义各自单调。

**推荐**：**立即做**（九条里唯一的纯产品缺口，且它让"单机用户体验"与"集群体验"一致）。

### 缺口 9 · 连接器与外部数据案例 —— 大部分今天可做；callout 要做一次确定性抉择

**现状（事实与实测）**：

| SDF 示例 | moonflux 侧现状 | 判定 |
| :--- | :--- | :--- |
| `helsinki-transit`（MQTT 订阅源） | MQTT 订阅源已就位（P19，含独立 Python broker 门禁） | **今天可做案例**（用仓库自带的测试 broker，不需外网） |
| `car-processing` / `ny-transit`（HTTP 源入湖） | HTTP 源已就位（**实测**：本地 `python3 -m http.server` → 变换 → stdout 通过） | **今天可做案例**；但它是**一次性 GET**（pull 一次即 `Exhausted`），SDF 的 http-source 是**间隔轮询** |
| `hackernews-notify`（HTTP 拉取 + RSS 解码） | 同上；RSS 解码属用户算子 | 可做案例（解码用一个 guest 算子） |
| Kafka 往返 | Kafka 源/汇已就位（P20，含独立 broker 门禁） | **今天可做案例** |
| `http-callout` / `openai-callout`（**逐记录** HTTP 调用，含 API key） | **沙箱无导入 ⇒ guest 不能做 IO**（结构性事实，不应破坏） | 需**宿主侧 `http` 变换**（见下），且与确定性冲突 |

**方案 A（小票）· 轮询 HTTP 源 —— 已落地（2026-10-10，T109，决策 57）**

实现：`{"type":"http","url":…,"interval_ms":N}`（0/缺省 = 原一次性语义）；轮询期 `pull` 返回 `Quiet`（**永不说 `Exhausted`**，否则"轮询器"就退回成一次性源），到点才重取，每批按其**取数时刻**打时间戳（与 MQTT 源的到达时间口径一致）；重取同一份 body 会**重复投递**同样的记录——去重是读者的事，与任何外部轮询器一致。证据：`core/spec` 解析测试（缺省/正数/负数/非数值四态）、案例 09 的 `spec-poll.json`、`scripts/e2e-p30-connector-examples.sh` 腿 7（两次 200ms 轮询 → 至少两批、进程仍存活、主题按批增长）。

**方案 A 原设计记录（保留）**：给 HTTP 源加 `interval_ms`（0 = 现在的行为）：`{"type":"http","url":"...","interval_ms":1000}`，`Quiet` 语义与 MQTT 源同形（三态 pull），每轮重取并交付。门禁：本地 HTTP 服务端 + 两轮取数 + 停止后 `Exhausted`/`Quiet` 行为符合三态契约。

**进展（2026-10-10）**：三类案例已落地并进门禁——`examples/sdf/{09-http-source,10-mqtt-transit,11-kafka-bridge}`，由 `scripts/e2e-p30-connector-examples.sh`（6 腿）验真，对端是仓库自带的 `python3 -m http.server`、`scripts/mqtt_test_broker.py`、`scripts/kafka_test_broker.py`（无需外网）。案例同时把落差写进 README：SDF 的连接器在数据流之外，moonflux 的连接器就在 spec 里。**方案 A（轮询 HTTP 源）仍是小票**，**方案 B（callout）仍未立项**。

**方案 B（中票，须先选边）· 宿主侧 `http` 变换（callout）**：`{"type":"http","url":"...","method":"GET|POST","cache_ms":N}`——IO 留在 adapters（net-native 已有 HTTP 客户端），**沙箱保持纯净**。必须同时定义：

- 期限与体量上界（P12/§15 纪律：出站必须有期限）；
- **凭据只做参数、永不入日志/审计**（P12 纪律；SDF 用 `std::env::var("OPENAI_API_KEY")` 从沙箱读环境，我们**不抄**）；
- **确定性抉择（本方案的核心，必须显式选边）**：
  - **(i) 接受非确定性**：`http` 变换标注为"外部效应、重放不保证"，要求 opt-in 开关，且门禁只断言结构（调用次数/失败 fail-closed/超时不挂死），**不断言响应内容**；
  - **(ii) 记录-回放（cassette）**：把响应按请求指纹落盘（或落主题），重放时命中记录——**确定性得以保留**，代价是存储与失效策略，以及"什么时候允许真调"的策略面。
- 建议：**先 (i) 并在文档里写明边界**（与"墙钟只报告"同源：不把不可复现的东西接进 pass/fail），把 (ii) 作为需要时的演进。

**推荐**：**案例先做（MQTT/HTTP/Kafka 三例，小票）**；轮询 HTTP 源小票；callout 作为独立里程碑且必须先选边。

## 4. 每条的开场纪律（写进 ticket 时必须先答）

1. **它进 core 吗？** 状态与窗口**不能**进 core 的解析/计算红线之内读时钟或 IO；状态存储属于宿主（apps/adapters），窗口由注入的事件时间驱动。
2. **确定性怎么保？** 缺口 1/2 由"重放决定旧值 + 事件时间来自记录"保证；缺口 9 的 callout 明确是例外，必须选边并写进文档与门禁（门禁只断言结构）。
3. **门禁断言什么？** 一律结构事实（重启后一致、逐字节一致、fail-closed、拒绝按名、计数与偏移），**不断言耗时**（决策 41）。
4. **是否破坏既有不变量？** 状态主题与 compaction/retention/复制的关系、多汇与偏移语义、主题源与"一节点一拓扑"——每条都要在本票里显式回答，回答不了就不动。

## 5. 与对标的关系（AGENTS §7）

- 追平的是**能力**，不是**语义假设**：键提取必须显式声明（不抄 SDF 的签名嗅探）；窗口无 idle 触发器照抄其文档边界并写明；状态不藏在服务里而是**日志里的物化视图**（这比 SDF 更"可重放"，是本项目自己的取向）。
- 明确**不做**的三件（SQL 引擎、组件模型、仓库内 Rust 工具链）要写进 §5 与 feature-matrix，避免下一轮被"顺手做掉"。
