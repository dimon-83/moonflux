# moonflux 生产就绪度评估（快照）

> **定位**：对当前快照（P0–P26）的**生产就绪度评估**——分级结论、支撑证据、会变成事故的缺口、以及不开发新功能即可执行的最小生产化清单。**规约依据**：AGENTS.md §10（证据与状态规范）；**边界声明**：本文是**评估**，不是能力承诺——能力状态的单一真相在 [`feature-matrix.md`](feature-matrix.md)，对标语义在 [`compatibility-matrix.md`](compatibility-matrix.md)，进度在 [`project-roadmap.md`](project-roadmap.md) 与 [`progress-board.md`](progress-board.md)。结论只对文末「评估方法与局限」列出的证据范围成立；未做的验证（压载 / 长稳 / Linux）不在此承诺。
>
> **日期**：2026-10-10 · 评估对象：P0–P29（门禁 46 步绿，native 293 / wasm-gc 190；CI 两腿均已绿）；P21–P29 的交付项按维护规则回填第 2/3/4 节（复核留痕见 §5）

## 1. 分级结论

- **受控场景下可以**（内部管线、单机房、受信网络、有人看护、RF≥2）：数据面的正确性与耐久性证据是完整的——应答前落盘、逐帧 CRC、撕裂尾截断恢复、复制逐字节一致、故障注入门禁全绿、至少一次语义无缺口。可以把数据托付给它。
- **通用/对外/合规场景不可以**：缺口集中在**运维面与工程面**（控制面单点、无可观测端点、**Linux 只验到 fast 层**、无发布工程）——**原先点名的开发缺口已清**（P21 ACL/审计、P24 无重启轮转、P25 压缩相继落地），剩下的基本都是部署与流程工作，不是功能开发。
- **一句话**：它现在能替你**保住数据**，但还不能替你**值夜班**。

## 3. 会变成事故的缺口（不开发功能就一直在）

1. **控制面单点**（最大风险）：SC 单进程、元数据单文件（`metadata.json`），无 HA、无备份/恢复工具。SC 宕机 = 消费组冻结、无新提名、无法建主题（**数据面继续服务**，P11 有腿证实）；SC 磁盘损坏 = 主题声明永久丢失。
2. **平台与工程面**：远端仓库已就位（94 笔提交推送）；**CI 已接线**（2026-09-27）——`fast` 在 Linux 上随推送运行并首绿，`full` 手动于 macOS；**Linux 因此从"从未验证"收窄为"fast 层已验证"**：四后端编译（wasm/wasm-gc/js/**native**）与两套测试在 ubuntu 上通过，但仍**没有在 Linux 上跑过 E2E**（那 31 条腿按 BSD 用户习惯写，只在 macOS runner 上跑——2026-09-27 首次手动跑满 43/43）；唯一产物仍是 debug 构建；无版本/打包/安装/升级面，滚动升级未测。
3. **可观测性**：无 metrics、无健康端点——监控只能刮日志、用 CLI 轮询（`group describe` / `cluster offsets`）。
4. **合规面**：~~按主题/用户的 ACL 与审计日志~~ **已交付（P21，2026-09-25）**；~~证书轮转~~ **已交付（P24：mtime 热重载，新连接用新材料、在途连接不受影响）**；**SASL 为边界声明而非缺口**（决策 48：token-over-TLS 覆盖同一威胁，明文端口由启动警告明示；Kafka 连接器侧的 SASL/TLS 是互操作候选）。
5. **容量与成本**：单线程每进程（容量按主题/节点手工切分）；~~无批压缩~~ **Kafka 侧已交付（P25：DEFLATE 进 `core/codec`、gzip 双向、炸弹上界）**，**自有 MFS 帧与段文件仍不压缩**（决策 49 的显式边界而非遗漏——压自有协议要先重定义预算语义）；单机 `serve` 恒 RF=1，**不能当生产数据面**（生产须 `sc` + `spu`，RF≥2）。
6. **平台细节**：macOS 的 `fsync` 只到驱动缓存（`F_FULLFSYNC` 才是真落盘）——"ack 即落盘"完整成立的前提是 Linux，而 Linux 恰好未验证（回到第 2 条）。
7. **运维手工性**：无 K8s operator / systemd 单元；压实需显式触发；无优雅退出（但 kill 是安全的——恢复语义兜底，门禁每天在杀）。

## 4. 最小生产化清单（不开新功能，配置与运维可补）

- [ ] 拓扑：`sc` + ≥2×`spu`，RF=2；**不用**单机 `serve` 承载生产数据
- [ ] 安全：`auth.json`（TLS + token）+ 角色分离（写/Root 最小化）；网络边界隔离
- [ ] 备份：定期快照 SC 的 data dir（一个 `metadata.json`）；接受"SC 挂掉期间协调面短暂停"
- [ ] 看护：外部编排（systemd/容器）+ 日志采集；用 CLI 轮询做消费滞后与水位探针
- [ ] 调优：按负载调大生产批（吞吐 ↔ fsync 成本）
- [ ] 已知接受项（书面化）：**自有协议不压缩**（P25 边界）、SASL 未做（token-over-TLS 替代）、组随 SC 停机冻结、升级 = 停机重启（同版本协议 v2）

## 5. 评估方法与局限

- **已做**：通读耐久性关键路径（`core/log` 的 append/flush/恢复/压实）；结论逐条回链门禁腿或实测（P17/P18 的基准与洞实验）；对平台级事实（fsync 语义、无端点、无信号处理）做了源码核对。
- **未做（不在此承诺）**：压载与长稳（无 soak/longevity 测试）、混载下的延迟抖动分布、Linux/生产内核上的完整门禁、跨版本升级、磁盘满 / fd 耗尽 / 时钟回拨等极端场景的注入。
- **使用方式**：把本评估当**上线评审的输入清单**，不要当通过证书；每轮里程碑收口后复核（与 [`progress-board.md`](progress-board.md) 同步）。
- **本轮复核（2026-09-25）**：按维护规则复核第 2/3/4 节并回填 P21–P26 的交付项（ACL/审计、证书轮转、Kafka 侧压缩、ABI v2 标量）；第 1 节的分级结论随之改写（开发缺口已清，剩下的是运维与工程面）。**未重新评估**的是第 3 节第 1/3/6/7 条（控制面单点、可观测性、fsync 语义、运维手工性）——它们与 P22–P26 无关，仍然成立。
- **本轮复核（2026-09-27）**：CI 接线后按证据更新 §2（新增"持续集成"行）与 §3 第 2 条——Linux 从"从未验证"收窄为"**fast 层已验证**"（四后端编译 + 双测试套件在 ubuntu 上通过，run `36324100660`），但 31 条 E2E 腿仍只在 macOS 上跑。缺口等级未变（仍不可对外），变的是**可证伪的范围**：上一轮这里写的是"CI 未接线、Linux 从未验证"两句声明，现在它们各自有了清单与边界。
- **本轮复核（2026-10-10）**：P27（编辑器函数集 UI）、P28（后台压实加入维护节拍）、P29（SDF 示例集应用案例与 Studio 提案）均未触及第 2/3 节的结论——前两者是产品面与存储运维面的收口，后者是**对标表达能力的压力测试**：它产出的 9 条缺口（服务内键控状态、窗口/水位、SQL、arrow-row state、Rust 工具链、split 拓扑、topic 源、函数集本地创建、云侧连接器）里只有最后一条是平台缺口，其余都是有意的范围边界。**对生产就绪度的判断不变**：能在受控场景托付数据，不能对外承担 SLA。
