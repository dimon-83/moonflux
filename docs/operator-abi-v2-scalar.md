# 算子 ABI v2：标量调用设计稿（只设计不实现）

> 定位：**不可信标量函数的沙箱路线**——ABI v1（批记录算子）的加法扩展设计。
> 规约依据：AGENTS.md §8.1（ABI 定稿即契约）/ §8.2（函数集纪律）；决策依据：README 决策 27（函数集资产）、28（本设计稿）、50（落地）。
> **状态：已实现（2026-09-25，P26）**——触发条件（用户提交的标量函数需求）成立。落地实录与开放问题结论见 §7；实现相对本稿的两处修正（返回通道、上限语义）已先改本文件再改代码，见 §7.1。日期：2026-09-17；落地：2026-09-25。

## 1. 动机：为什么需要第二条标量路径

现状两条执行位置各有明确边界：

| 路径 | 语义 | 信任前提 | 预算 | 现状 |
| :--- | :--- | :--- | :--- | :--- |
| mbel 函数集（宿主侧） | 标量、逐记录、可复用 | **可信资产**（平台评审后部署） | mbel limits（节点/深度/步数）+ 递归 256 | ✅ 已实现（P6） |
| 算子 ABI v1（wasmtime 沙箱） | 批记录变换 | 任意（无导入、结构性纯） | 记录数 + fuel（分级） | ✅ 已实现（P2） |

两者之间的空档是**"用户提交的标量函数"**：它既要标量的粒度与可复用性（函数集的价值），又必须有无导入沙箱的隔离（v1 的价值）。把 mbel 塞进沙箱（mbel-in-guest）是另一条路，但那要先把 mbel 编译成 guest 可加载的形态，且把表达式引擎的演进耦合进 ABI；**先设计一个薄的标量调用协议**，让 guest 侧用什么语言实现成为实现细节，是更小的承诺。

## 2. 形态：v1 的加法扩展

**v1 的 7 个批导出一个不改**（`mf_op_abi_version` / `mf_op_alloc_input` / `mf_op_init` / `mf_op_process` / `mf_op_output_len` / `mf_op_last_status` / `mf_op_last_error`）。v2 新增**可选**导出，仅当宿主需要标量调用时才要求它们存在：

| 导出 | 签名（概念） | 说明 |
| :--- | :--- | :--- |
| `mf_op_scalar_abi_version` | `() -> i32` | 标量 ABI 版本；缺失 = 该模块不提供标量调用（v1-only 模块继续可用） |
| `mf_op_eval` | `(ptr, len) -> i64` | 一次标量求值：入参是请求字节，返回输出长度（`< 0` = 结构化错误码，错误文本走 `mf_op_last_error`） |

**请求/应答编码（首版）**：JSON 文本，`{"fn":"tax","args":[12.5,0.2]}` → `{"v":2.5}`。理由：与函数集资产的 JSON v1 同源、可读、便于对拍；**二进制编码列为开放问题**（见 §5），因为逐记录 JSON 解析是热路径成本。

**缓冲协议沿用 v1 的既定事实**：宿主无法伪造 guest 的 Bytes（boxed 指针 + 头部），因此仍由 guest 持缓冲（`mf_op_alloc_input` 语义不变：宿主写入、guest 读取），输出长度单独暴露。标量调用是"一次分配 + 一次调用 + 一次读回"。

## 3. 宿主侧：函数注册表与逐调用预算

```
registry : Map[函数名 -> ScalarBinding{ module_path, budget: BudgetTier,
                                          max_calls_per_batch, fuel_per_call }]
```

- **解析时机与 v1 一致**：spec 引用函数**名**（沿用 `$.spec.transforms[i].functions` 的引用面），宿主在 **apply 时**解析注册表并绑定 revision/版本（决策 27 的绑定纪律同样适用：绑定发生在 apply，不隐式热更新）。
- **每个标量调用独立安装 fuel**：`fuel_per_call` 与批预算**分开**——批预算是"这一批最多烧多少"，标量预算是"这一次求值最多烧多少"。两者都超限即 `BudgetExceeded`，不报裸 trap。
- **宿主侧 mbel 闭包 ↔ guest 的 marshal**：宿主把 `@ast.Value` 编成请求 JSON、把应答 JSON 解回 `@ast.Value`；**类型映射表**是契约的一部分（`StrVal`↔string、`NumVal`↔number、`BoolVal`↔bool、`ArrayVal`↔array；`BytesVal`/对象值首版不支持，遇即 `EvalError`）。
- **失败一律 fail-closed**：guest trap / 拒绝 / 预算超限 / 编码错误 → 结构化 `EvalError` → 记录不放行（与 v1 的批次 fail-closed 同一条纪律）。

## 4. 确定性

- guest **无导入**（无 WASI / 无时钟 / 无随机）是**结构性事实**，v1 已由 `tools/probe_operator_exports.py` 以编译器 WAT 为真相源钉住；v2 继承这条门禁，新增导出必须同样无 import 段。
- fuel 是确定性计量（无时钟），同一批数据重放得到同一结果——与内核红线同源。
- **函数集资产（决策 27）的纯度策略不适用于 v2**：沙箱里的 guest **本来就读不到时钟**，所以不需要文本扫描；两侧的保证方式不同、方向一致。

## 5. 开放问题（实现前必须回答）——结论见 §7.2（2026-09-25）

1. **编码**：JSON 首版的逐记录解析成本（每次求值一次 parse + 一次 stringify）。候选：长度前缀的二进制标签编码；或"批量化"（见 3）。
2. **标量调用的批量化**：逐记录跨边界调用是 N 次 alloc/call/read；把"一批记录的多个求值"打包成一次 `mf_op_eval` 调用（请求是数组）能把边界成本摊薄——但会让协议从"函数调用"变成"批处理"，与 v1 的边界重叠，需要先有量测再定。
3. **错误分类**：目前只有"结构化错误 + 文本"。是否值得像 v1 那样给出稳定的错误分类码（参数类型错 / 越界 / 预算 / trap）？
4. **注册表治理**：函数名到模块的映射谁来写（spec？节点配置？元数据？）；同名跨模块冲突如何拒绝；revision 如何像函数集一样单调。
5. **参数类型**：mbel 的表达式体函数**没有参数类型声明**（按调用点推断，ticket 36 §评估校核实测）——沙箱形态应当**显式带类型**（请求里的 args 自带 JSON 类型，guest 自己校验），这条差异要在文档里说清楚，避免使用者以为两侧语义相同。
6. **与 mbel-in-guest 的关系**：若未来要"把表达式引擎放进沙箱"，v2 的标量协议可以成为它的载体（guest 内嵌 mbel）；那是一次独立的立项，不在本设计稿的承诺内。

## 6. 明确不做（本设计稿的边界）

- 不实现任何导出、不改宿主代码、不加 spec 字段（**引用面沿用函数集的 `functions`，直到有需求再立新字段**）。
- 不改变 v1 的 7 个导出与批协议语义；v2 是**加法**，不是替代。
- 不做 mbel-in-guest；不做函数集的集群分发；编辑器不加相关 UI。

## 7. 落地实录（2026-09-25，P26）

### 7.1 实现相对本稿的两处修正（先改本稿，再改代码）

1. **返回通道**：§2 的表把 `mf_op_eval` 的返回写成"输出长度"。实现时发现长度单独暴露仍需一个
   指针出口，而 v1 早已有现成的拆分——**调用返回答案缓冲的指针（guest Bytes 降为 i32，与
   `mf_op_process` 的返回同构），长度走既有的 `mf_op_output_len`，失败走既有的
   `mf_op_last_status`/`mf_op_last_error`**。导出面仍是两个（不新增第三个），且与 v1 的
   缓冲协议逐字同构——"沿用 v1 的既定事实"这一条按字面执行。
2. **每批调用上限的语义**：`max_calls_per_batch` 计的是**每次链调用拿到的记录数**。
   `pipeline run` 原来把链**逐记录**调用（每条记录一个单元素批）——这既让上限永不触发，也
   让 v1 的批算子在数据路径上一直只拿到单条批。P26 修成整批应用（这是门禁腿 6 逼出来的：
   上限的测试写不出来，说明它的语义没有被任何路径行使）。**serve 的取数路径保持逐条目
   应用**（偏移随条目走，窗口预算与 ReplyPacker 的交织），因此那条路径上的上限恒不触发、
   真正的界是"每次链调用一条记录"本身——如实写在 `scalar_registry.mbt` 的注释里。

### 7.2 开放问题结论

1. **编码**：JSON 文本落地（首版设计）。逐记录 parse/stringify 是热路径成本，**接受并留痕**；
   二进制编码在量测显示必要时单独立项（当前无量测）。
2. **批量化**：不做。请求是单函数单求值；与 v1 批边界重叠的方案需要先有量测。
3. **错误分类**：最小分类落地——求值失败经 `last_status=1` 走结构化 `EvalError`（文本含
   函数名与原因）；请求不可解码在 guest 内被拒（文本含 "request:"）；fuel 超限**不是码**，
   表现为 trap 由宿主映射 `BudgetExceeded`（与 v1 同一映射，门禁沿用）。
4. **注册表治理**：节点侧文件 `<data-dir>/scalar-functions.json`（`revision` + 函数数组：
   `name`/`module`/`tier`/`max_calls_per_batch`；未知字段、重复名、非法 tier 都在加载期拒绝）。
   **apply 时解析绑定**（决策 27 纪律）；未注册的名字在 apply 失败并给出注册表路径；
   v1-only 模块注册为标量函数同样在 apply 被拒（"ABI v1-only"）。控制面 publish 用控制面
   自己的注册表检查一遍，节点用自己的一份再查一遍（权威是副本，不是唯一守门人）。
5. **参数类型**：`ScalarKind` 显式声明（KStr/KNum/KBool/KArr），guest 在求值前**显式校验**
   ——与 mbel 的调用点推断不同，这一点写在 SDK 注释与本文；记录值作为**字符串**过界
   （record → args 的丰富映射等真实用例再设计）。
6. **mbel-in-guest**：不在本里程碑（本稿 §6 的边界不变）。
