# 算子 ABI v3 设计稿：键控状态（以及窗口如何骑在它上面）

> **定位**：给 moonflux 补上九条缺口里的第 1 条（**服务内持久键控状态**）与第 2 条（**窗口与水位**）的设计。**规约依据**：AGENTS.md §5（内核红线：零 IO、确定性）、§8.1（算子沙箱纪律：ABI 加法、guest 无导入、双预算、fail-closed）、§7（对标规则）。**边界声明**：本文是**设计稿**——按 P26 的惯例（"先改稿再改码"），先定稿再实现；文中每一条"必须"都要在实现时变成门禁腿，做不到的就改设计而不是放宽门禁。
>
> **日期**：2026-10-10 · 状态：**设计中（未实现）**

## 0. 一句话

**状态不是服务里的一个新对象，而是一条压实过的键控主题；算子通过 ABI v3 把"这批记录的当前状态"当数据收下、把"新状态"当数据交回。** guest 依旧没有导入——状态是数据进出，不是 API 调用。窗口不需要宿主特性：它是"键 = `key@窗口起点`"的普通状态用法，加上一条由**事件时间**推进的水位规则。

## 1. 为什么不是 SDF 的 state 对象

| 维度 | SDF | 本设计 |
| :--- | :--- | :--- |
| 状态的持久化 | 服务内的 state store（arrow-row/scalar 两种 API），由平台管理 | **压实过的键控主题**——复用既有日志、复制、压实、floor |
| 恢复 | 平台从 store 恢复 | **重放状态主题**（上界 = 键数，不是记录数） |
| 复制 | 平台复制状态 | **既有分区复制**，一行代码都不用改 |
| 跨服务读 | `states.X.from` | 消费那条状态主题（今天就能做）；宿主侧 `lookup` 变换是后续候选 |
| 谁拥有"最新值" | state store | **压实**：每键最新，偏移不变（决策 38） |

这不是"用另一种写法做同一件事"：SDF 的状态对象是**平台的第二份持久真相**；本设计坚持**日志是唯一持久真相**（README 决策 31 的直系推论）。代价写在 §7，不藏。

## 2. 语义

1. **键来自记录的 key**。状态更新以记录的 `key` 为键；**空 key 拒绝**（结构化错误，指出记录偏移/位置）——不发明第二套键提取面（不抄 SDF 的签名嗅探）。
   *SDF 的 `partition.assign-key` 在本设计里对应什么*：**批算子可以给它输出的记录设置 key**（信封里的记录本来就带 key；今天的 `operator-flatmap` 选择继承源记录的 key，但换个算子就可以把它设成每个 token）。因此"先分词再按键计数"这类数据流 = `flat-map（设置 key）→ 状态算子`，不需要 `state.key` 这种第二套提取面。这条要在实现时用一个"设置 key 的算子"钉住（否则示例会显得只能吃预先打好键的输入）。
2. **状态主题是该 spec 声明的一条普通主题**（spec 的 `state.topic`），节点的压实策略对它生效；`state.topic` 与数据主题**必须不同**（同名即拒绝：源与状态的环）。
3. **状态值是不透明字节**，与记录值同口径。宿主不解释它；空值 = 删除该键（一条"墓碑"记录，压实后仍保留最新即墓碑）。
4. **每个批是一次事务**：批内所有记录的状态读来自**批开始时的视图**（批内不互相看见），批结束时一次性写回状态主题。这样"同一批的顺序"不影响结果，重放可复现。
5. **确定性**：状态转移只依赖（输入记录、批开始时的旧状态）。旧状态由状态主题的重放决定 ⇒ 同输入同输出（内核红线的直接推论）。
6. **失败 fail-closed**：算子返回失败 ⇒ **记录不落 sink、状态不写回**（半批不落地的既有纪律扩展到状态）。

## 3. 线格式（加法段，不升 v1/v2）

沿用"帧里的可选段"纪律（P18/P22 的先例：段缺失 = 空表，不升版本）：

```
输入信封 v3 = [记录批 v1][状态段]
状态段     = uleb 条数 + 每条 (key_len, key, value_len, value)
输出信封 v3 = [记录批 v1][状态段]        // 宿主只在该模块声明 v3 成对导出时读写
```

导出（**可选且成对**，与 v2 同一条纪律）：

```
mf_op_state_abi_version() -> Int          // 1
mf_op_state_apply(input_ptr) -> ptr       // 走 v1 的 alloc/output_len/last_status/last_error
```

- 只出一个 = 模块损坏（构建门禁拒绝）；一个不出 = v1/v2 模块照旧。
- `mf_op_process` 与 `mf_op_state_apply` **互斥**：宿主按导出选择调用，spec 的同一节点不会既要求状态又走无状态路径。
- 预算：状态段计入既有的批预算（`MAX_BATCH_BYTES` 的派生），**不新增第二个数字**（决策 39）。视图有上限（§5）。

## 4. 宿主侧（apps，不进 core）

| 组件 | 职责 | 不进 core 的理由 |
| :--- | :--- | :--- |
| **状态视图** | 启动时从状态主题的 floor 起重放，构建 `键 → 最新值`；批处理后按新状态增量更新 | 需要日志 IO |
| **写回** | 每批把变更写为键控记录追加到状态主题（`key = k`） | 需要日志写入 |
| **厚度控制** | 视图条目上限（默认 100k 键，`MOONFLUX_STATE_KEYS` 可调）；超限**结构化拒绝**并指出上限，绝不静默淘汰 | 策略属于宿主 |

- 视图是**缓存**，主题是**真相**：任何不一致都以主题重放为准（P16 的"打开一次、句柄归缓存"同源纪律）。
- 状态主题的 retention 由应用给定；`cluster compact` / 后台压实对它同样生效（P28）——"每键最新"因此天然是状态的物化形态。
- 视图重建是 O(状态主题可读记录数)：这是 **floor 的意义**——压得越紧，重启越快。

## 5. 窗口：不是宿主特性，是库用法

- **窗口键 = `<key>@<窗口起点>`**（窗口长度由用户声明，单位毫秒，按事件时间切分）。
- **水位 = 已见最大事件时间**（`max(record.timestamp)`，单调不回退）——它是**输入的函数**，因此确定。
- **闭合规则**：当某条记录把水位推过某窗口末端时，该窗口可输出；输出记录的 timestamp = 窗口末端（决定论意义上最自然的取值）。
- **没有 idle 触发器**：没有新记录就没有水位推进，也就没有闭合——这与参考系统自己的文档边界一致（`word-counter` 的 README 把"没有静默触发器"写成已知缺口），也是"无宿主时钟"下的唯一自洽选择。
- **迟到记录**：默认**计入其所属窗口并重新输出该窗口**（至少一次口径；消费方按键幂等）。策略可配：`drop`（丢弃并**计数报告**）。无论哪种都**必须报告**，不得静默。
- SDK 提供 `@sdk.tumbling_session(len_ms)` 之类的薄助手（纯计算：算桶、维护水位、决定何时发射），宿主对此一无所知。

## 6. 门禁形态（每条都必须可证伪）

| # | 断言 | 形态 |
| :--- | :--- | :--- |
| 1 | 状态跨进程重启存活 | 跑一批 → 杀进程 → 重启 → 读状态主题重放 → 同一批再跑，输出与状态逐字节一致 |
| 2 | 状态主题被压实后最新值不变 | 多版本写同一键 → `cluster compact` → 视图重建后值不变、幸存偏移不变 |
| 3 | 确定性 | 同输入跑两遍（各自全新 data dir）→ 状态主题与 sink 输出逐字节一致 |
| 4 | 空 key 拒绝 | 无 key 记录进状态算子 → 结构化错误含键缺失原因，且**状态未写回** |
| 5 | 视图上限 | 超过上限时结构化拒绝（含上限值），不静默淘汰 |
| 6 | fail-closed | 算子失败 ⇒ 记录不落 sink 且状态主题无新记录 |
| 7 | v3 成对 | 只导出 `mf_op_state_apply` 的模块被构建门禁/探针拒绝 |
| 8 | v1/v2 不受影响 | 既有 `crosscheck-operators.sh` 与 ABI 探针全绿（回归） |
| 9 | 窗口闭合 | 事件时间推进跨过窗口末端 ⇒ 恰好一次输出该窗口；无新记录 ⇒ 不输出（idle 边界） |
| 10 | 迟到策略 | `drop` 时计数报告；默认重发时输出重复可见（至少一次） |
| 11 | 状态与复制的交互 | 两副本各自重放状态主题得到逐字节一致的视图 |

## 7. 代价与边界（写清楚，不藏）

- **写放大**：每次状态变更一条记录（这是"日志即真相"的账单）。压实把它收敛到每键一条。
- **视图是 O(键数) 内存**：上限与拒绝语义是显式的；超过就该换设计（分片/外部存储），而不是让宿主偷偷淘汰。
- **批内不可见**：同一批里的两条记录看不到彼此的状态更新（§2.4）。要顺序语义就把批拆小（或将来引入"逐条状态算子"，那是显式提案）。
- **没有跨服务状态对象**：跨服务读 = 消费状态主题（今天可做）。宿主侧 `lookup` 变换（按记录键查状态视图并合并）是后续候选，**不在本设计内**。
- **没有 SQL**：查询是消费方的事（`sdf-gap-closure-plan.md` §5 的判定不变）。窗口也不引入查询语言。
- **与 SDF 的等价性**：能力等价（键控状态 + 窗口），**架构不等价**（日志是真相 vs 平台第二份真相）。文档与案例 README 都必须这么说。
