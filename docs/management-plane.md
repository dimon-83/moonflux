# 管理平面 / 数据平面：任务生命周期与多任务治理（P37-5 的完整形态）

> 这份稿回答一个问题：moonflux 现在是"命令行工具 + 一个只读控制台"，怎么长成
> **能启动常驻进程、管理多个任务、有可视化界面、协调 worker 工作平面**的管理平面。
> 用户的直觉是对的：**可以类比 K8s 的控制面/数据面**，而且 moonflux 已经有一半了——
> 缺的不是重新发明，而是把"任务"从"手动启动的进程"升级成"控制面调度的工作负载"。

## 1. 类比是忠实的，但有四条要划清

| K8s | moonflux 的对应 | 现状 |
| :--- | :--- | :--- |
| apiserver + etcd（期望状态库） | `sc` 的元数据（`topology.json` 任务集 + 主题声明，**单文档级修订**） | ✅ 已有 |
| controller-manager（对账） | `sc` 的主题放置/选主调和 | ✅ 已有（数据面存储） |
| scheduler（把 pod 放到 node） | `sc` 把**任务**放到节点 | ⏳ **缺**（今天任务手动启动） |
| kubelet（在 node 上跑容器、上报） | 节点（`spu`/`serve`）承担 **runner 角色**：按控制面分配起/停子进程 | ⏳ **缺** |
| pod 状态 | `run list`（P37-2：running/stopped/offline，优雅停止与被杀可区分） | ✅ 已有 |
| kubectl | `moonflux` CLI | ✅ 已有 |
| Dashboard | 控制台页（`web/editor`：任务/运行/拓扑三个面板） | ✅ 骨架已有，待扩 |

**四条刻意的不同（不是缺陷）**：

1. **没有 CRD、没有 etcd**：期望状态就是**任务集文档**（`topology.json` v2），声明式、
   一个修订、整份采纳——K8s 把同一件事拆成一堆 CRD，moonflux 用一份文档。
2. **任务是进程，不是容器**：runner 是**进程监督**（起子进程 `pipeline run`、SIGTERM 优雅停、
   退出即按策略重启），不是容器运行时。Docker 是**可选形态**（决策 87 已具备），不是基座。
3. **控制面不主动拨号数据面**：分配随**心跳应答**下发（与现有主题放置同一机制）——
   这是 P3/P13 的硬纪律，调度任务也照此办理。
4. **状态即日志**：任务的状态（`run list`）与记录（`<task>.run-log`）都已是**主题**，
   所以"任务重启不丢状态"是现成的性质，不是要新造。

## 2. 现状盘点（哪些已经在了，别重复造）

- **控制面 `sc`**：主题声明→放置、选主、复制、资产下发（任务集/函数集，pull 不 push）、
  运行注册表（`run list`）、`/metrics` 与 `/healthz`、角色鉴权（Root/ReadOnly/Node）+ TLS。
- **数据节点 `spu` / 单机 `serve`**：宿主分区、复制、压实、消费组、运行表。
- **任务本身**：`pipeline run`（源→主题→变换→汇、状态主题、运行登记 `--control`、
  轮询与退避重试（决策 94）、SIGTERM 优雅停止即"注销"）。
- **多任务**：`topology.json` v2 是**任务集合**（P37-1），一个数据目录持有一组任务。
- **控制台**：任务清单 / 运行表 / 只读拓扑三个面板（P37-3），经 WS 连一个 broker，
  内核渲染、页面不解析协议（P4）。

**缺的只有三块**：① 把任务**放到某个节点**的调度与对账；② 节点上的 **runner 角色**
（真的去起/停进程）；③ **生命周期命令面**（start/stop/status/logs）＋控制台的操作按钮。
这三块就是 P37-5 的完整形态。

## 3. 目标架构

```
                    ┌────────────────────────────── 控制面（sc）──────────────────────────────┐
                    │  期望状态：任务集文档（+ 每任务 target: node|any, restart 策略）         │
                    │  对账循环：desired(文档) vs actual(run list)                            │
                    │            → 该起的起、该停的停、死了的按策略重启、丢了主人的重分配      │
                    │  调度：把任务许给某个节点（沿用心跳应答下发，不主动拨号）               │
                    └───────────────────────────────────────────────────────────────────────┘
                                     ▲ 心跳(分配+修订)    │ 运行登记(run report)
                                     │                    ▼
   ┌─────────────── 数据面：节点（spu / serve，含 runner 角色）──────────────────┐
   │   child 进程: pipeline run --name <task> （每任务一个子进程，被节点监督）     │
   │   起/停 = fork/SIGTERM；退出 = 上报；崩溃 = 节点上报 offline、sc 按策略重启   │
   │   状态：run list（running/stopped/offline） · 记录：<task>.run-log 主题       │
   └─────────────────────────────────────────────────────────────────────────────┘
     ▲  日志/状态
     └── 控制台（web/editor，外部静态托管 + WS）── 任务清单 · 运行表 · 拓扑 · 操作按钮 · 节点视图
```

**要点**：控制台和 runner 都**不是第二个控制面**（ticket 纪律 ✓），不新增端口、不新增
第二套命令语义——一切走现有 MFS 会话与 WS 网关。

## 4. 关键设计决策（每条都落到现有纪律上）

1. **runner 是节点的角色，不是新进程**（kubelet 类比）：`spu`/`serve` 已经在跑、已经连着
   控制面、已经有一个数据目录——让它们**宿主任务子进程**，比再造一个 `agent` 少一个要
   监督的进程、少一套身份。任务子进程与节点隔离：任务崩了不拖垮节点（反过来节点崩了，
   控制面按心跳超时把它判离线、重分配它的任务，与现有节点故障同一路径）。
2. **放置沿用心跳下发的机制**：节点从心跳应答里读到"分配给我的任务集合"（与"分配给我的
   分区"同一条路）；本地多出的任务停下、缺了的起，这就是对账的**节点那一半**。
   **控制面那一半**：文档里 `target: node|any`（首期不做亲和/容量打分，只做存活过滤 +
   简单循环），任务没有合法节点时留在 pending 并**在状态里可见**（不静默）。
3. **生命周期命令面**（Root 类）：`task start|stop|status|logs --remote sc`。
   `stop` 走 SIGTERM → 优雅停止 → run-stop → 注销（P37-2 已有）；`status` 就是 `run list`
   的一个投影；`logs` 读 `<task>.run-log`（**把 `pipeline run` 的 stderr 也追加进 run-log**，
   这样"看日志"从控制面一处就够，不用登到节点上）。
4. **重启策略是期望状态的一部分**（诚实版本，不假装有 K8s 的 restartPolicy 全套）：
   `restart: never|on-failure|always`（默认 `on-failure`）。崩溃→offline→控制面按策略决定
   是否再起；`never` 的任务死就死了、状态里如实标 offline。
5. **首期明确不做**（都写下来，不静默）：任务**副本**（同任务多份，涉及去重语义，另立项）、
   自动扩缩容（缺指标与判据，先只报告）、滚动升级（任务集整份采纳、原子切换，不做逐任务灰度）、
   任务到节点的**亲和/反亲和**。
6. **可视化 = 扩控制台，不是新造**：在现有面板上加"节点视图 + 任务生命周期按钮 + pending/离线
   高亮 + 每任务日志侧栏"。页面仍只渲染内核给的模型（P4）：生命周期按钮→发 MFS 命令、状态→
   读 `run list`、日志→读 run-log，**页面不实现任何调度逻辑**。

## 5. 分阶段（各自独立收口，对应 P37 ticket 的 P37-5）

| 期 | 内容 | 门禁（可证伪） |
| :--- | :--- | :--- |
| **P37-5a** | 生命周期命令面 + runner 角色：`task start/stop/status/logs`；节点起/停子进程、SIGTERM 优雅停、退出上报 | 起→登记→有输出；停→列表变 `stopped` 且**扛过回收窗口**；`kill -9`→`offline`；logs 能看到 run-log + stderr；权限（ReadOnly 不能 start/stop） |
| **P37-5b** | 调度与对账：`target: node|any` + restart 策略；控制面 desired/actual 对账、故障节点重分配 | 把任务许给指定节点并在该节点起；停掉节点→其任务被判 offline→按策略重启/重分配到活节点；pending 状态可见；文档变更触发停旧起新 |
| **P37-5c** | 控制台操作面板：节点视图 + 生命周期按钮 + 日志侧栏 + 指标 | 页面按钮真的发出命令（对端断言 ✓）；页面状态 == `run list`/`task list` 同源；不做像素门禁 |
| 之后 | 任务副本 / 滚动升级 / 亲和 / 自动扩缩容 | 各自立项 |

每期都遵守：**门禁纳入 `gates.sh`、文档同步（README 决策 / feature-matrix / roadmap / board /
本稿 / ticket）、CI 四条腿全绿、边界如实写下**。

## 6. 一句给操作员的画面（做完全貌后）

```bash
moonflux task start --remote sc --name inlet-cod-stuck      # 或"文档一 apply，调度器自己起"
moonflux task status --remote sc                            # 哪些 running / stopped / offline / pending
moonflux task logs  --remote sc --name inlet-cod-stuck      # run-log + stderr，一处看全
# 控制台：任务清单上点"启动/停止"，运行表实时变，异常离线高亮，日志侧栏可读
```

管理平面（sc + 调度 + runner 角色）管**任务**，数据平面（节点）跑**数据与任务**，控制台只是
观察与操作的窗——这就是你说的"类比 K8s"，而底座是 moonflux 自己的声明式状态 + 对账，
不是 K8s。
