# 45 — 稀疏索引

**What to build:** 每段一份 `.idx` 稀疏索引（每 N 条记录或每 M 字节记一条 `offset→position`），
`read(from)`/`read_raw(from)` 先按段表定位，再按索引跳到最近锚点向前扫描——不再整文件读入。
**正确性优先**：索引只是加速器，缺失/损坏/不一致时回退全扫，且两条路径结果必须逐字节一致（门禁对拍）。

- [x] `SegmentFile` 增追加/读取索引的能力，或由 `SegmentStore` 提供 `index_file(base)`（二选一，实现时定并留痕）
- [x] `read`/`read_raw` 走索引：段内 seek → 前扫；跨段继续；`read(0)`、`read(from=段边界)` 等边界用例
- [x] 单测：索引路径与全扫路径结果一致（随机起点/长度）；索引被截断/写坏 → 回退且结果不变；索引与段的
      偏移不一致（人为篡改）→ 回退而非错答

### 关账（2026-09-17）

**二选一的决定（本票要求留痕）**：索引由**存储层**提供独立的索引文件（`SegmentStore.open_index(base)`），
不是塞进段内——理由是 `remove(base)` 必须把两者一起删掉（孤儿 `.idx` 是等着骗读者的谎），而"同生共死"
属于存储层的责任。fs 适配器落在同目录的 `<base>.idx`（命名与段一一对应，一眼可见配对）。

格式（version 1，写死并校验）：`MFI1` | seg_base(8,BE) | count(4,BE) | (offset 8BE, position 4BE)×count |
crc32(4,BE)。**CRC 覆盖全部前文**——一个"看似合法但被写坏"的索引会被检出而不是被信任。
锚点策略：每 `index_every_records` 条记录、且至少每 `INDEX_EVERY_BYTES`（4KiB）一个锚点；锚点**永远落在
帧边界**（写入前记录，构造上成立）。

**优雅降级**：任何疑虑都回退到扫描——缺失、长度不符、magic 不符、base 不符、CRC 不符、锚点非单调、
position 越界，全部 `None`；open 时封存段（已滚走的段）尝试读 `.idx`，失败即扫描重建（**重建后写回**，
自愈）；最后一段本来就要扫（恢复），顺便重建其锚点，零额外成本。封存（roll）是写索引的时机——段此
后不再变化，落盘的东西才一直为真。

**测试**（`core/log_test` 20/20）：① 锚点/非锚点起点逐个偏移读，与全序列一致；raw 路径与记录路径一致；
② 索引**全部删掉** → 重建，结果不变；③ 索引**截断 4 字节** → 回退，结果不变；④ 索引**翻转一位**（CRC
失效）→ 回退，结果不变；⑤ 锚点覆盖每段且 `.idx` 体积有界（<200B：是锚点不是全量映射）。
