# 64 — P13 门禁逼出的两个真 bug

**Status:** done (2026-09-17)

两个都不是 P13 引入的，而是 P13 的门禁（+ 采样）逼出来的既有缺陷。记在这里，因为它们比本里程碑本身更重要。

## ① 复制拨号在握手期间不泵 → 环状死锁（既有缺陷，P13 期间变为必现）

**现象**：P7 门禁（3 分区 RF=2 跨 3 节点）稳定失败——所有节点都 `handshake: deadline`，客户端访问任一数据
节点超时。用 `sample <pid>` 采样卡住的节点，栈是 100% 的
`SyncLink::connect → await_frame → poll_fds → poll`。

**根因**：`SyncLink::connect` 的手写握手用 `idle_pump = fn() { () }`（不泵），注释理由是"我们还没有在途请求，
没有自己的连接要服务"。这句推理漏了**对端**：你等 WELCOME 的时候，可能正是别人在等你的节点。三个节点在环上
同时拨号，于是互相等待、无人 poll——每一次都耗满 1s 期限，下一个 tick 再来一遍（链接永远建立不起来）。
这正是 P7 已经解决过一次的"节点互相听不见"，只是漏在了**唯一不泵的路径**上。

**修法**：把调用方的 `pump` 传进 `connect`（握手期也泵）。顺带删掉从无调用者的 `SyncLink::redial`
（`opens` 因此不再需要 `mut`——它是"这次拨号的计数"，不是可变累计）。

**证据**：修前 P7 连续 3 次红；修后连续 2 次 9/9 绿，全量门禁 31/31。

## ② 写向已消失的对端 → SIGPIPE 杀进程（既有缺陷）

**现象**：P13 门禁跑一半控制面**进程消失**，客户端拿到 `Connection refused`；进程退出码 **141**（= 128+13，
SIGPIPE），日志里没有任何 panic —— 因为它不是异常，是信号。

**根因**：垫片用 `send()` 写，没有 `MSG_NOSIGNAL`（Linux）也没设 `SO_NOSIGPIPE`（macOS）。任何"对端在 poll
与 write 之间消失"的连接都能把整个服务端杀掉。P13 的沉默探针（握手到一半就退出）正好制造了这个窗口；
TLS 走上写路径后概率更高（`SSL_write` 内部也是 `send()`）。

**修法**：垫片在创建/接受 socket 的入口调一次 `mf_net_ignore_sigpipe()`（`signal(SIGPIPE, SIG_IGN)`，
进程级、幂等），让写失败变成 `EPIPE`——即所有调用点本来就在处理的那种错误。注释写清"这不是防御性代码，
这是修复"。

**教训**：门禁红的时候，先问"它是不是在告诉我别的事"。腿 1 的红色最终指向的是两个与"控制面调度"无关的
缺陷：一个死锁、一个信号。
