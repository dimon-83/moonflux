# 62 — hub：每轮至多一次 TLS 握手 + 期限可配

**What to build:** `ConnectionHub::poll_once` 现在**一次性 drain 全部 backlog**，而每次 `adopt()` 在有 TLS 时
做一次**有界阻塞握手**（`HANDSHAKE_DEADLINE_MS`）——于是 N 个"连上不说话"的连接 = N×期限 的停摆，
这就是 P12 观测到"健康节点被误判离线"的机制。

- accept 循环：**每轮至多尝试一次** TLS 握手（明文 accept 不设限——它不阻塞），其余留在 backlog
  （对端已连上，只是还没被采纳，不产生客户端可见失败）；
- `handshake_deadline_ms` 成为 hub 的参数（默认 2000；`sc` 用 500ms），构造函数/`with_tls` 之外加
  `with_handshake_deadline(ms)`；
- 注释写下**为什么**：停摆上界 = 每 tick 一个期限，与探测者数量解耦；并如实注明剩余边界（一次有意的
  连接洪泛仍可挤占 backlog——单线程服务端共有的性质，真正的 DoS 治理属后续需求）。

### 关账（2026-09-17）：**原方案是错的，被门禁否掉了**

票面写的是"每轮至多一次 TLS 握手"。实现后门禁腿 1 **红**——不是差一点，是机制不对：

- 门禁腿 1（8 个沉默探针 + 3 个节点，7s 窗口内不得出现 offline/election 行，判据是 SC 日志症状计数）
  在三种实现下分别跑到：**drain 全部（原行为）→ 红**（4×500ms 停摆错过 3s 存活窗）；
  **每轮 1 次 → 红**（停摆有界了，但**队头阻塞**：沉默连接占着 backlog 的位置，真实节点的连接要排在它们后面才被
  adopt，于是节点自己的调用超时，3s 后照样被判离线）；**不等待（步进式握手）→ 绿**。
- 结论写进代码注释与门禁：**限制"每轮等几次"改不了"等"本身**，只要握手是阻塞的，沉默对端总能通过 backlog 伤害
  真实客户端。正解是**根本不等待**：`adopt` 只 attach（socket 先转非阻塞），连接进入 `TlsHandshake` 阶段，
  每轮由 `step_handshake` 推进一步（`SSL_accept` 在非阻塞 socket 上立即返回 want-read/want-write，一步不成就
  下一轮再来），期限到了才丢弃。一个沉默对端于是只值"每轮一次立即返回的调用"。
- 因此 `MAX_HANDSHAKES_PER_ROUND` **不存在**（不是被调小，是被删掉）：没有阻塞，就没有要预算的东西。
  `handshake_deadline_ms` 作为 hub 参数保留（`sc` 用 500ms，`serve`/`spu` 用 2000ms），它现在的含义是
  "多久算沉默"而不是"允许多少停摆"。

可证伪性留痕：门禁腿 1 在两种错误实现下都**会红**（上面三次运行即证据），所以它不是一条"怎么写都绿"的腿。
