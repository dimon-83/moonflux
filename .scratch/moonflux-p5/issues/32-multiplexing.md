# 32 — 连接多路复用（事件循环）

**What to build:** 把"accept → 处理到连接结束 → accept 下一个"改成**事件驱动多连接**：所有活跃连接
一起 poll，谁有数据就给谁推进协议状态机；空闲/挂起的连接不占用其他人的服务时间。仍然是单线程
（不引入 async 运行时），与既有的"节点循环 + 定时家务"形态一致。

**Blocked by:** 无（P4 门禁暴露的缺口）。

**Status:** ✅ done (2026-09-17)

- [x] `net-native` 原语：`set_nonblocking`、`recv_some`（would-block 与 0 字节/错误可区分）、
      `poll_readable(fds, timeout_ms)`（返回就绪下标）；带单测（多 fd 并发、超时、挂起 fd 不影响其他）
- [x] 每连接状态机：入口缓冲 + 帧解析 + 应答排队；**部分帧不阻塞整环**（半个头到达也能等下一轮）
- [x] `serve`：accept 循环改为注册到事件循环；HTTP 升级（WS）在事件循环内完成，升级后按 WS 帧推进
- [x] `spu` / `sc` 同样接入（同一个循环实现，避免两套）
- [x] 慢客户端策略：写缓冲有上限，超限断开并报告（不能因为一个不读的客户端吃满内存）
- [x] 门禁 `scripts/e2e-p5-concurrency.sh`：浏览器长连接（或等价的挂起 WS 连接）+ 2 个 CLI 客户端
      并发 produce/consume 全部成功；一个"连上但不读"的客户端存在时，其他客户端延迟仍在秒级

## 落地记录

- **形态：poll 驱动的事件循环（不是线程）**。`ConnectionHub`（`apps/cli/hub.mbt`）持有所有活跃连接，
  统一 poll：谁有数据就推进谁的协议状态机；**半个帧留在缓冲里等下一轮**，谁都不阻塞谁。
  应答进每连接的 outbox，按 socket 可写性排空（`send_some` 返回 0 = 缓冲满 = 下一轮再写），
  所以一个只写不读的对端也不能把循环卡住。
- **适配层新增原语**（`adapters/net-native`）：`set_nonblocking`、`recv_some`/`send_some`
  （**would-block 与 EOF 与错误三者必须可区分**——事件循环的正确性建立在这条上）、
  `poll_readable(fds, timeout)`；均有单测，其中一条专门断言"沉默的 socket 不影响其他就绪判定"。
- **命令实现只有一份**：hub 只决定处理器**何时**运行，不改变它**做什么**——`dispatch_session_frame`
  就是单连接路径那套分发逻辑；HTTP 升级与帧会话是同一台状态机的两个状态，因此浏览器与 CLI
  由同一个循环服务。
- **慢客户端策略**：outbox 超过 8MiB 判定对端不读，**带日志断开**（不能让一个不读的连接吃掉进程内存）。
- **`spu`/`sc` 仍是有意单连接**，并已在代码注释里写明理由（对端已知且少：控制面 + 该分区的
  follower 轮流拉取；把复制路径整体移植到 hub 需要额外小心）——**记录而不是遮掩**。
- **本轮踩的两个真 bug**：
  1. hub 第一版把 **WebSocket 帧的载荷当成了会话帧**——WS 帧是信封，里面装的才是 `MFS` 帧；
     混淆后每个命令的 cmd 都是 0，PRODUCE 直接失败。修法：每连接两个缓冲（socket 原始字节 +
     解封装后的载荷），帧解析器只看后者。
  2. 升级被拒时**先关连接再写 400** ⇒ 客户端什么也收不到。修法：拒绝也入 outbox，且关闭前
     一律先 flush（"再见也要说得出口"）。
- **门禁**：`scripts/e2e-p5-concurrency.sh` 六条腿全绿——空闲 WS 连接不饿死 CLI；纯沉默连接不拖慢他人；
  两个 CLI 并发都成功；发半个帧后挂起不影响循环；WS 会话与 CLI 交错各自正确；服务端日志确认走的是
  并发循环。已纳入 `scripts/gates.sh`（22 步）。
- **关键回归**：P4 编辑器门禁的断言阶段现在**在浏览器连接仍然打开的情况下**通过
  （验证时端口上有 2 条 ESTABLISHED）——这正是当初不可能的场景；`e2e-p4-editor.sh` 里
  "关掉标签页再跑 verify" 的临时绕行说明已删除。
